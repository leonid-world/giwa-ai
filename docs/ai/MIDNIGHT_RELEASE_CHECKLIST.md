# 최종 제출 전 저장소·공개 주소 정리

기록일: 2026-09-15. 상태: **후속 작업으로 보류 — 아직 실행하지 않음**.

사용자는 기능 작업을 몇 가지 더 진행한 뒤, 최종 제출 전에 저장소와 Vercel
이름·주소를 정리하기로 했다. 현재 개발 중에는 이 체크리스트를 먼저 실행하지
않는다. 최종 제출 준비를 시작할 때 다시 읽고, 새 클론 빌드와 공개 데모
재검증을 마칠 시간을 확보하여 진행한다.

## 잊지 않도록 설정한 상기 방법

2026-09-15 사용자가 아래 두 방법을 승인했고 설정을 완료했다. 저장소·주소
전환 자체는 여전히 후속 작업이며, 알림이 그 작업을 자동 실행하지 않는다.

- **제출 준비 시 확인:** 루트 [AGENTS.md](../../AGENTS.md)에 최종 제출·
  제출 준비·제출 링크 정리를 요청받으면 이 문서와 TODO를 먼저 읽고 미완료
  항목을 상기시키도록 규칙을 추가했다. 일반 기능 개발 중에는 전환을 앞당기지 않는다.
- **예약 알림:** 2026년 **9월 24·25·26·27일, 매일 오후 8시(Asia/Seoul)**에
  이 대화에서 최신 문서와 완료 근거를 확인하고 남은 작업을 알려준다.
  자동화 이름은 `Midnight 제출 전 저장소·주소 정리 알림`, ID는 `midnight`다.
  같은 상태라도 요청한 각 날짜에 미완료 작업을 한 번 상기시킨다.
- 완료 근거가 확인되거나 사용자가 최종 제출 완료/알림 중지를 알리면 자동화를
  일시 중지하도록 지시했다. 9월 27일 이후에는 예정된 실행이 없다.
- 로컬 문서를 읽는 예약 작업은 컴퓨터와 Codex 앱이 실행 중이어야 한다.
  앱의 Scheduled에서 알림 설정과 실제 실행 결과를 확인할 수 있다.

설정 생성과 저장된 일정은 확인했다. 미래 알림의 실행·전달 완료를 뜻하지 않는다.

## 정리 방향

- 기존 GASOK 저장소와 제출 이력은 보존한다.
- Midnight 제출용 **새 공개 저장소 하나**에 프론트·백엔드·Midnight·기존
  계약 등 필요한 소스를 일반 폴더로 모은다. 내부 저장소를 따로 받아야 하는
  서브모듈 구조를 제출 저장소에 그대로 옮기지 않는 방향이다.
- 새 저장소의 기본 브랜치 `main`을 Midnight 제출 버전으로 사용하고,
  이후 Midnight 개발도 이 저장소에서 이어간다.
- 기존 Vercel 프로젝트의 이름과 공개 주소도 최종 프로젝트명에 맞춘다.
  배포는 기존 Vercel과 Railway 통합 앱·MySQL 구성을 유지한다.
- 프로젝트명은 **MidProof**로 확정했다(2026-09-17). 저장소명·소유자,
  공개할 파일/이력 범위와 도메인은 추후 확정한다. 주소 사용 가능 여부는 미확인이다.

새 저장소는 심사자가 코드를 쉽게 받고 실행하도록 하기 위한 구성이다.
새 이름이나 저장소만으로 신규성 또는 이전 코드 재사용 자격이 확보되는 것은
아니다. 공식 요구사항과 미확인 규정은
[해커톤 제출 안내](MIDNIGHT_HACKATHON_SUBMISSION.md)를 함께 확인한다.

  재사용 허용 범위와 신규 작업 기간 규정도 최종 제출 전에 확인한다.

## 2. 제출용 단일 저장소 준비

- [ ] 현재 작업 폴더와 별도의 준비 경로에서 제출 소스를 구성한다.
  실행·빌드에 필요한 모든 내부 소스와 Compact 빌드 자료가 포함되는지 확인한다.
- [ ] 원래 저장소와 기준 커밋, 이후 추가 변경을 문서/커밋으로 추적할 수 있게
  보존한다. 새 저장소를 만들었다는 이유로 기존 코드를 새 개발로 설명하지 않는다.
- [ ] 공개 대상 파일과 가져올 이력에 비밀값이 없는지 확인한다.
  `.local`, DB 덤프, 지갑 seed·개인키·암호화 상태·저장 암호·capability 키,
  실제 환경 파일과 배포 인증정보는 소스와 함께 게시하지 않는다.
- [ ] 필요한 소스가 일반 파일로 추적되도록 구성하고 `main`에 제출 버전을
  커밋한다. 폴더명 변경 등 실행과 무관한 리팩터링은 이 작업에 섞지 않는다.
- [ ] README에 소개·Midnight 구현 포인트·기존 코드 대비 기여·실행 방법·
  도구 버전·환경변수 예시·데모 역할/지갑 준비·가상 기관의 한계를 정리한다.
- [ ] 준비한 범위로 새 공개 저장소를 게시하고 About 설명과
  `midnightntwrk` 토픽을 설정한다. 제출 URL과 정확한 커밋을 기록한다.
- [ ] 비로그인 상태에서 새 저장소를 일반 `git clone`으로 받아 필수 소스가
  모두 포함되는지 확인한다. 작성자 PC의 ignored 상태 없이 의존성 설치,
  필요한 빌드·테스트와 README 실행 절차를 검증한다.

## 3. 기존 배포를 새 저장소·주소에 맞춤

- [ ] Vercel 프로젝트명과 공개 도메인을 새 이름에 맞춘다.
  프로젝트 표시 이름만 바꾸고 제출 URL은 그대로 남기는 일이 없도록 확인한다.
- [ ] 새 저장소를 이후 배포의 기준으로 삼고, 기존 Vercel의 소스 연결·
  Production 브랜치·프론트 Root Directory를 확인한다. Railway는 통합
  Dockerfile이 있는 새 저장소 루트에서 기존 앱으로 배포하는 경로를 검증한다.
- [ ] 기존 환경변수, Railway `/data` 볼륨과 MySQL을 유지한다.
  저장소/도메인 정리를 위해 지갑·계약·DB를 새로 만들거나 초기화하지 않는다.
  같은 지갑 상태를 사용하는 로컬 앱과 Railway를 동시에 실행하지 않는다.
- [ ] 새 프론트 origin을 Railway의 `CORS_ALLOWED_ORIGINS`와
  `MIDNIGHT_DEMO_ALLOWED_ORIGINS`에 반영하고 실제 배포에서 확인한다.
- [ ] README·제출 폼·영상/Deck 링크와 canonical·OG/Twitter·sitemap 등
  공개 주소 참조를 새 도메인에 맞춘다. 기존 주소의 유지/리다이렉트 여부를 정한다.
- [ ] 새 주소에서 로그인 버튼, 준비 완료 표시, 요청/응답과 공개 결과 조회를
  확인한다. MetaMask의 새 사이트 연결 및 역할 지갑 서명도 실제로 확인한다.
- [ ] 최종 배포 버전에서 실제 증명→Preview 기록→요청자의 결과 조회를
  리허설한다. 기존 완료 결과 조회·메모리 증명 검사와 새 체인 제출을 구분해 기록한다.
  제출 시점에 시연 요청과 결과가 만료되지 않았는지도 확인한다.
